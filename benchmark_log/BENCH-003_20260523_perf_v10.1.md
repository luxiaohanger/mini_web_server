### 5.3 热点摘要

| 占比（约） | 符号 / 函数 | 说明 |
|------------|-------------|------|
| ~4.3% | `EventLoop::loop` → `Connection::onHttp` → `ThreadPool::enqueue` → `futex_wake` | I/O 线程解析后投递 worker，条件变量唤醒 |
| ~4.1% | `sendHttpOnLoop` → `trySendToSck` → `Buffer::bufferToSck` → `write` | 响应写回 I/O 线程，`bufferToSck` + syscall |
| ~3.9% | 内核 `__tcp_transmit_skb` / `net_rx` / softirq | loopback TCP 发送与收包软中断，随写路径连带 |
| ~8.8% | `[k] _raw_spin_unlock_irqrestore` | 内核锁解锁，分布在 futex 与网络栈路径 |
| （次要） | `Channel::handle`、`std::function` 调用 | epoll 回调分发开销 |

**用户态结论：** 最热业务路径是 **HTTP 双跳跨线程**（I/O → ThreadPool → I/O 写）与 **写 socket 路径**；`HttpProcess::parse` / `buildResponse` 未出现在采样栈前列，当前 Echo 响应体下 **线程调度 + 写 syscall** 优先于解析。

## 7. 结论与下一步

- **v10.1 目标达成**：Keep-Alive 负载下完成 perf 采样，符号可解析（`Connection` / `Buffer` / `EventLoop` 可见），Lost Samples = 0。
- **瓶颈判断**：CPU 主要在 **(1) onHttp 投递 ThreadPool 的 futex 唤醒** 与 **(2) sendHttpOnLoop 写路径（含内核 TCP）**；Echo 场景解析不是首要热点。
- **v10.2 建议方向**（择一或组合验证）：
  1. **减少双跳**：合法 GET / 静态响应在 I/O 线程直出（或合并 enqueue 次数），降低 `ThreadPool::enqueue` + `enqueueTask` 频率；
  2. **写路径**：预构建固定 HTTP 响应、`writev`/减少 `std::string` 拷贝、写缓冲攒批；
  3. **ThreadPool**：降低 cond 竞争（任务队列/唤醒策略），需与架构边界权衡。
- **下一步**：选定 v10.2 变更 → 改代码 → BENCH-004 纯 wrk 复测对比 BENCH-002。
