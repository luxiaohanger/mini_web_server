# 高性能 Buffer 设计：数据流转与 `readv` 优化

在 Reactor 架构中，`Buffer` 类不仅是数据的容器，更是连接 **内核 I/O** 与 **业务逻辑** 的桥梁。本项目实现的 `Buffer` 采用了**动态扩容**、**平移复用**以及 **`readv` 散射读取**技术。

## 1. 核心数据结构

`Buffer` 内部维护一个 `std::vector<char>`，并使用两个索引（Index）来标识数据状态：

* **`readIdx`**：指向可读数据的起始位置。
* **`writeIdx`**：指向可写空间的起始位置。
* **数据区间**：
* `[0, readIdx)`：已读数据区（死区）。
* `[readIdx, writeIdx)`：可读数据区（业务逻辑取走的部分）。
* `[writeIdx, capacity)`：可写空间（从 Socket 存入的部分）。



---

## 2. 散射读取优化：`sckToBuffer`

这是本类最核心的性能优化点。为了解决“无法预知内核缓冲区数据量”的问题，我们使用了 Linux 系统调用 `readv`。

### 实现逻辑

我们同时提供两个缓冲区给内核：

1. **第一缓冲区 (Primary)**：`Buffer` 内部剩余的可写空间。
2. **第二缓冲区 (Secondary)**：栈上的临时空间 `extrabuf` (64KB)。

### 优势分析

* **零拷贝（Zero-Copy 近似）**：如果数据量小于 Buffer 剩余空间，数据直接由内核写入堆内存，无需经过用户态中转。
* **减少系统调用**：64KB 的额外空间确保了即使面对突发大流量，也能通过一次 `readv` 调用清空内核缓冲区。
* **精准扩容**：只有当数据真正溢出到 `extrabuf` 时，才调用 `dataIn` 进行动态扩容，避免了盲目 `resize` 带来的开销。

---

## 3. 数据转移机制

### 3.1 自动扩容与平移 (`dataIn`)

当新数据进入 `Buffer` 时，遵循以下策略：

1. **直接写入**：如果剩余空间足够。
2. **内部平移**：如果“死区”（`readIdx` 之前的空间）加上剩余空间足够，则将存活数据前移到 `index 0`，回收死区。
3. **动态扩容**：如果物理空间确实不足，调用 `vector::resize`。

### 3.2 缓冲区间转移 (`bufToBuf`)

在 `Connection` 逻辑中，常需要将 `readBuffer` 的数据转移到 `writeBuffer`（例如 Echo 服务）。

* 该方法同样支持**平移复用**和**自动扩容**。
* **应用场景**：解耦了接收逻辑与发送逻辑，业务层可以先将响应数据拼装在 `writeBuffer` 中，等待 Socket 可写事件触发时一并发送。

## Q & A


1.为什么设计 Socket 类？

> 设计原则：底层简单可靠，上层灵活多变

- 将 socket 系统调用全部封装在类内部，提供接口给上层调用；
- 将 fd 封装在类内部，负责控制 fd 的生命周期，外层类一般不持有裸露的 fd，而是控制 Socket* ,符合 RAII 资源管理思想；
- 同时保持 Socket 类的简洁轻便，业务逻辑由调用类负责，保持底层类的通用性


------

2.为什么设计 Buffer 类？

故名思义，buffer 是缓冲而非存储，因此其中的数据是流式的、一次性的，写入 buffer 的数据流入后段，等待其他业务逻辑读取的数据在前段。

业务逻辑读写数据少量多次，不适合频繁系统调用 read()/write()，使用 buffer 就可以一次性读写大量数据

> 只有 fd 的读写才用到系统调用，其他的拷贝、转移在用户态

- 1. **解决粘包半包**：暂存断续字节流，确保业务层拿到完整的协议逻辑包。
- 2. **削峰填谷解耦**：缓存网络波动数据，让底层收发与业务处理互不干扰。
- 3. **减少系统调用**：通过一次性批量读写，降低用户态与内核态切换开销。
- 4. **支持非阻塞写**：暂存内核无法立即接收的数据，防止业务逻辑产生阻塞。
